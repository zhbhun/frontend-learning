# 性能与基准

yjs 本体的算法开销很低——这是官方 crdt-benchmarks 用真实编辑轨迹测出的结论。协作系统的实际性能,更多取决于使用方式:同一批写入怎么提交、update 日志怎么积累与压缩、删除在文档里留下什么、内容插在文档哪个位置。本课先用官方结论建立量级预期,再对每个「杠杆」跑可复现的微基准,最后落到大文档场景的实践判断。

自测数字的口径:除注明出处外,均为 yjs 13.6.33 + Node 24.13.0 + Apple M5 实测,脚本在本课程目录 `bench-*.mjs`(预热后多次取中位数),可自行复跑;浏览器实例读数是单次运行,与脚本中位数略有出入属正常。

```mermaid
flowchart LR
  E[编辑操作] --> T[事务提交<br>粒度杠杆]
  T --> U[增量 update<br>编码格式杠杆]
  U --> L[update 日志<br>存储 / 网络 / 重放]
  L --> C[定期压缩<br>mergeUpdates / 快照]
  C --> D[加载与同步]
```

| 杠杆 | 何时生效 | 实测量级(本课示例环境) | 手段 |
| --- | --- | --- | --- |
| 事务粒度 | 循环写入逐条提交 | 1 万次 `map.set`:约 20 ms vs 3 ms,update 10,000 条 vs 1 条 | `doc.transact` 包批 |
| 日志积累 | 持久化 / 传输只追加增量 | 2,000 次编辑:增量合计 65 KB | `mergeUpdates` / 定期快照 |
| 墓碑 | 内容被删除 | 全删 100 KB 内容:gc 文档快照 26 B;`mergeUpdates` 仍 100 KB | 快照要过 gc 文档(默认) |
| 编辑落点 | 中段 / 随机编辑 | 同样内容:尾部追加 15 KB / 1 条,中段 77 KB / 3,999 条 | 认知即可,通常由用户决定 |
| 编码格式 | V2 编码 | 结构化数据 -34%,碎片化文本 -69%,整块纯文本 ≈ 0% | `encodeStateAsUpdateV2`(实验性) |
| 批量导入 | 逐字符 append / 逐条 push | 5 万条:整段插入不到 1 ms,逐条追加(Text)20–31 s、逐条 push(Array,2 万条)1.9 s | 整段 `insert` |
| 结构深度 | 深嵌套 vs 扁平 | 4,000 叶子 `applyUpdate` 1.3–2.1 ms,差异不显著 | 不必为性能强拍扁 |

## crdt-benchmarks:官方基准怎么说

[crdt-benchmarks](https://github.com/dmonad/crdt-benchmarks) 是 Yjs 作者 Kevin Jahns 维护的基准仓库,用同一套场景跑主流 CRDT。本文引用时 README 的数据条件:Yjs 13.6.11、Automerge 2.1.10、Loro 0.10.1、ywasm 0.9.3,Intel i5-8400 @ 2.80 GHz,Node 20.5.0;`memUsed` 用 GC 前后堆差近似,不含 wasm 内存。

四组场景:B1 无冲突顺序编辑、B2 双人并发冲突、B3 多客户端 Map/Array 并发、B4 真实编辑轨迹回放(一篇 LaTeX 论文的编辑记录:182,315 次单字符插入 + 77,463 次单字符删除,最终文本 104,852 字符;B4x100 放大到约 1,050 万字符)。B4 的关键读数:

| 指标 | Yjs | Automerge 2.1.10 | 说明 |
| --- | --- | --- | --- |
| 应用全部编辑 | 5,714 ms | 14,326 ms | Loro 0.10.1 为 3,089 ms |
| parseTime | 39 ms | 1,805 ms | 解析 update 字节的开销,yjs 低一个数量级以上 |
| docSize(gc 后) | 159,929 B | 129,116 B | 全量编码体积 |
| B4x100(千万字符级) | 608,908 ms / 327.1 MB | 未测 | 旧版 Automerge 0.14.1 为 489,104 ms / 1.1 GB |

再加两条:

- **每字符编辑的增量极小**:README 各表中 yjs 的 avgUpdateSize 约为每字符编辑 27–36 B;本课示例环境自测逐字符插入约 20 B(中文、单客户端),量级一致。
- **包体积**:yjs 69 KB(gzip 20 KB)对比 Automerge 1.74 MB(gzip 604 KB),前端加载预算差一个数量级。

引用这批数字的三个边界:

- 数字绑定版本与硬件,换版本、换机器、换场景都会变;关注相对量级,不做绝对承诺。
- README 注明 Automerge 若把全部编辑放进单个事务会快得多——基准刻意按「逐笔编辑」模拟真实用户,这对所有实现都是更严苛的负载。
- B4x100 的重放是分钟级:千万字符级文档的加载成本真实存在,这正是后面「日志与压缩」要解决的问题。

## 事务粒度:一次提交一条 update

事务是 yjs 的计费单位:每次非空事务提交,产生 1 次 observe 回调、1 条增量 update——网络上的一条消息、持久化的一条记录([事务与变更事件](?path=/docs/transactions-and-events--docs)讲过它的生命周期)。循环写入不包 `transact`,N 次写入就变成 N 条 update、N 次事件、N 次编码与 N 条消息:

```ts
import * as Y from 'yjs';

const doc = new Y.Doc();
const map = doc.getMap('m');
// 1 万次写入,一条 update:1 次事件、一次编码、一条消息
doc.transact(() => {
  for (let i = 0; i < 10000; i += 1) map.set(`k${i}`, i);
});
```

实测(1 万次 `map.set`,预热后取 5 次中位数,`bench-transaction.mjs`):

| 提交方式 | 耗时 | update 事件 | 增量合计 | mergeUpdates 后 |
| --- | --- | --- | --- | --- |
| 单事务 | 约 3 ms | 1 条 | 140,644 B | 140,644 B |
| 逐条事务 | 约 18–20 ms(5–8 倍) | 10,000 条 | 240,506 B(1.7 倍) | 140,644 B |

逐条多出的 1.7 倍流量全是事务头:`mergeUpdates` 合并后与单事务完全等大。多花的钱买的是「每条一个独立变更」,不是内容。

## 批量写入:整段插入,避免平方级

逐条调用不只是事务数的问题。实测中两类写法是平方级的:

- `Y.Text` 逐字符追加:相邻插入会被合并进同一个字符串条目(见官方 README 的缓解措施),每次合并都要复制已合并的全部内容;
- `Y.Array` 逐条 push:每次 push 都要定位插入点,定位成本随数组长度增长。

整段调用一次装下全部内容,两种成本都消失:

```ts
text.insert(pos, wholeString);   // 而不是循环逐字符 insert
array.insert(0, items);          // 而不是循环逐条 push
```

实测(单事务包批,`bench-structure.mjs` 场景三):

| 写法 | 耗时 |
| --- | --- |
| Y.Text 逐字符追加(5 万次 insert) | 20–31 s |
| Y.Text 整段插入(1 次 insert) | < 1 ms |
| Y.Array 逐条 push(2 万次) | 1.9 s |
| Y.Array 整段 insert(5 万条) | 2–3 ms |
| Y.Map 逐键 set(5 万次) | 约 15 ms |

Y.Map 逐键写入是线性的,不必整段化;Text / Array 的循环写入必须合并成整段调用,或按块插入(比如每 1,000 条一段)。很多「导入脚本跑不完」的真正原因是这里,不是 yjs 本体慢。

## 日志与压缩:mergeUpdates 与快照

只存增量的存储与传输成本随编辑历史线性增长,加载等于重放全部日志。两档压缩,作用不同:

- `Y.mergeUpdates(updates)`:多条 update 合并为一条,去除重复头,不需要 Y.Doc;**不做 GC**——已删内容(墓碑)原样保留。
- **快照压缩**:把日志灌进一个(默认 gc 的)Y.Doc,再 `encodeStateAsUpdate` 全量编码——丢弃已删内容,并按最终物理布局重新编码。

实测(2,000 次中段文本编辑,`bench-compaction.mjs` 场景一):

| 形态 | 字节 | 加载(灌入空文档) |
| --- | --- | --- |
| 增量逐条合计(2,000 条) | 66,775 B | 约 4 ms |
| mergeUpdates(1 条) | 46,820 B | 0.6 ms |
| 快照(GC 后) | 78,728 B | 0.7 ms |
| 快照 V2 | 24,747 B | — |

两个反直觉点:

- 快照比 mergeUpdates 还大:中段编辑把字符串条目分裂成 3,999 个物理条目,快照按物理布局编码(下一节展开)。**两档压缩的取舍不在「谁更小」,而在「谁去墓碑」。**
- 逐条加载最慢:2,000 次 `applyUpdate` 的固定开销累积;合并与快照都在毫秒级——加载成本主要看总内容量,不必恐惧日志条数本身。

### 墓碑与 gc

删除不是移除:为了并发收敛,已删条目的位置元数据(id + 长度)永远保留;gc 决定的是**内容字节**是否跟着丢掉:

```ts
const gcDoc = new Y.Doc();                // gc: true 默认,删除提交即丢内容
const keepDoc = new Y.Doc({ gc: false }); // 保留已删内容,是否保留按业务取舍
```

实测(插入 10 万字符后全部删除,`bench-compaction.mjs` 场景二):

| 形态 | 插入后 | 全删后 |
| --- | --- | --- |
| gc=true 文档快照 | 100,016 B | 26 B |
| gc=false 文档快照 | 100,016 B | 100,026 B |
| mergeUpdates(插入 + 删除两条) | — | 100,026 B |

官方 README 说明的缓解措施:相邻插入合并为单个 struct、被删 struct 的内容替换为删除标记、被删类型的子结构转为可相邻合并的 GC struct。合起来读:**gc 之后文档也不会缩成「当前内容」**——墓碑元数据仍在,编码体积仍与历史总编辑量相关;gc 只切掉「已删内容」这块肥肉。

## 结构形态:编辑落点、嵌套深度与 V2

### 编辑落点:中段编辑产生碎片

同样 2,000 次编辑、同样约 11 KB 文本内容,只改插入位置(`bench-structure.mjs` 场景一):

| 落点 | 快照 | 物理条目 | 快照加载 |
| --- | --- | --- | --- |
| 尾部追加 | 14,905 B | 1 条 | 0.03 ms |
| 文档中段 | 78,728 B | 3,999 条 | 1.2 ms |
| 随机位置(固定种子) | 67,141 B | 3,305 条 | 1.3 ms |

机制:yjs 把相邻的同源插入合并成同一个字符串条目,追加型文档的物理布局只有 1 条;中段插入会把已有条目一分为二,几乎每次编辑都 +1 个物理条目。这是编码布局的固有差异,不是 bug,用户在哪里打字也通常不由开发者决定——它的价值是解释两个常见现象:

- 为什么文档编码比纯文本大几倍:多出的字节是碎片条目的定位信息(origin / rightOrigin / parent)。
- 为什么 mergeUpdates 与快照谁更小随场景摆动:一个保逻辑布局,一个保物理布局。

### 嵌套深度:实测不是杠杆

同样 4,000 个叶子,扁平一层、深套 8 层、按 40 / 400 组分桶(`bench-structure.mjs` 场景二):

| 组织方式 | applyUpdate | 编码 | 单键编辑增量 |
| --- | --- | --- | --- |
| 扁平 1 层 | 1.8 ms | 82,836 B | 33 B |
| 深套 8 层 | 1.4 ms | 86,919 B | 33 B |
| 分桶 40 组 | 1.4 ms | 81,838 B | 33 B |
| 分桶 400 组 | 1.7 ms | 86,179 B | 33 B |

差距在噪声级。按业务语义组织嵌套即可,不为性能把结构拍扁;结构真正影响的是可读性与 observe 事件路径(见[共享类型](?path=/docs/shared-types--docs)),不是编码与合入速度。

### V2 编码:碎片与结构化数据的压缩档

V1 / V2 是同一套 update 语义的两种编码,官方 README 说明 V2「提供更好的压缩」,并标注为实验性、勿用于生产。实测三组内容(`encodeStateAsUpdateV2`):

| 内容形态 | V1 | V2 | 收益 |
| --- | --- | --- | --- |
| 约 11 万字符连续文本 | 109 KB | 109 KB | ≈ 0% |
| 结构化数组(3,000 个对象中段插入) | 119 KB | 78 KB | -34% |
| 中段碎片文本(上节 2,000 次编辑) | 78,728 B | 24,747 B | -69% |

规律:内容越碎、结构化成分越高,V2 的差分编码越划算;整块连续文本本身已很紧凑,V2 无肉可榨。API 与使用边界见[文档更新与同步协议](?path=/docs/document-updates--docs)的 V2 一节:`encodeStateAsUpdateV2` 配 `applyUpdateV2`,`Y.convertUpdateFormatV1ToV2 / V2ToV1` 互转,两种格式不可混用。

## 大文档实践:量级、阈值与拆分

先定量感受「文档本体」的开销(20 万字符文本,分 200 段整段插入构建,`bench-structure.mjs` 场景四):快照 195 KB,全量编码 0.14 ms,灌入空文档 0.05 ms。官方 FAQ 的判断一致:对人工输入的文本,「Size is very rarely a practical problem」。

所以大文档的功夫不要花在「文档太大」的臆测上,先量三件真正会慢的事:

- **日志长度**:只追加增量的存储,重放与传输成本随历史线性涨 → 定期压缩;「快照 + 近期增量窗口」是常见的存储策略。
- **事件风暴**:高频细粒度事务让 observe 回调与网络消息爆炸 → 按事务粒度一节的方式包批。
- **批量导入平方级**:见批量写入一节。

拆分 subdoc(见[子文档](?path=/docs/subdocuments--docs))的判据不是性能,而是:

- **权限边界**:细粒度权限只能在文档边界强制,文档内部的共享类型做不到;
- **懒加载**:几百个互不可见的文档,不必随主文档一起加载与同步;
- **生命周期不同**:归档数据与活跃数据分开,压缩与备份各自独立。

FAQ 同时提醒:经常一起使用的数据放在同一份文档;拆分会带来加载协调与 Provider 支持成本,不为想象中的性能提前拆。

## 最佳实践

- 先测再优化,方法要对:预热、多次、取中位数——本课起草时 Node 首轮 JIT 曾把 0.7 ms 的加载测成 31 ms;浏览器实例读数是单次运行,`bench-*.mjs` 的中位数才是可复现口径。
- 分档压缩:去重用 `mergeUpdates`;瘦墓碑必须过 gc 文档做快照;对外分发与冷存储用全量快照。
- 写入侧三件事一起做:循环写入包 `transact`;Text / Array 批量装整段;高频交互按业务动作分包事务。
- 拆分按权限与加载边界,不按性能臆测:文档本体很少是瓶颈,日志与事件才是。
- 引用基准数字时带上条件:版本、硬件、场景;相对倍数比绝对毫秒更可迁移。

## 常见问题

- 文档越用越卡,加载与同步越来越慢?
  多半是 update 日志在涨,不是文档本体变慢:重放与传输成本随历史线性增长。把存量增量灌进一个 gc 文档再 `encodeStateAsUpdate`,之后按「快照 + 近期增量窗口」维持。
- `mergeUpdates` 压完没小多少,甚至比快照还大?
  两个原因:它不做 GC,已删内容原样保留;它保留逻辑插入布局,而快照按物理布局编码——中段编辑场景两者谁小随碎片程度摆动。目标是去重就用 `mergeUpdates`,目标是瘦身就过 gc 文档做快照。
- gc 开着(默认),文档编码为什么还是远大于当前内容?
  gc 只丢墓碑的内容字节;墓碑的位置元数据(id + 长度)必须保留,否则并发编辑无法定位。编码体积与历史总编辑量相关,随压缩周期回落,但不会降到「当前内容」级。
- 本地测出来的数字与本文、与 crdt-benchmarks 对不上?
  基准数字绑定 yjs 版本、硬件与场景(逐笔编辑还是批量事务),跨实现对比还受对方版本影响。复跑本目录 `bench-*.mjs`,关注相对倍数而非绝对毫秒。
- 批量初始化 / 导入脚本奇慢甚至跑不完?
  逐字符 `text.insert` 与逐条 `array.push` 都是平方级(字符串合并、定位成本随长度增长)。改成整段 `insert` 或分块插入;Y.Map 逐键 set 无此问题。

## 总结回顾

摘要:

本课把 yjs 性能拆成两层:本体开销与使用成本。本体开销用官方 crdt-benchmarks 定标——真实编辑轨迹回放 26 万次操作只要 5.7 秒,解析 update 字节 39 ms,包体积 20 KB gzip,每字符编辑增量几十字节;引用时必须带上版本、硬件与场景条件。使用成本有六个杠杆:事务粒度决定事件与消息条数(1 万次写入单事务 1 条 update,逐条 1 万条、慢 5–8 倍);批量写入要整段插入,逐字符与逐条 push 是平方级;update 日志靠 mergeUpdates(去重不去墓碑)与快照(过 gc 文档,真瘦身)压缩;墓碑的位置元数据永远保留,gc 只丢内容字节;编辑落点决定碎片化程度,同样内容编码可差 5 倍;V2 编码对碎片化与结构化数据收益最大但对连续文本无效,且是实验性的。文档本体很少是瓶颈:20 万字符编码与加载都在毫秒级;真正先慢的是日志长度、事件风暴和平方级导入,拆 subdoc 的判据是权限与加载边界,不是性能臆测。

一句话:

> yjs 本体很少是瓶颈——慢的是使用方式:逐条事务、只增不减的 update 日志、去不掉的墓碑和平方级的逐条批量写入;对应的手是 transact 包批、mergeUpdates 与定期快照、gc 文档、整段插入。

知识要点:

- crdt-benchmarks 的 B4 基准说明了什么?引用数字时必须带上哪些条件?
- 事务与 update 事件、网络消息的对应关系是什么?事务粒度影响哪几项开销,合并事务的代价是什么?
- `mergeUpdates` 与快照压缩各自做什么?为什么说取舍在「谁去墓碑」?
- gc=true(默认)时文档编码为什么不缩到当前内容大小?gc=false 用在什么场景?
- 编辑落点怎样让同样内容差出 5 倍编码与几十倍加载?嵌套深度实测影响多大?
- V2 编码在什么内容形态下收益大?使用边界是什么?
- 20 万字符文档的本体开销量级是多少?什么时候才真正考虑拆 subdoc?
- 哪些批量写法是平方级?正确的整段写法是什么?

## 参考示例

本课的基准脚本可直接复跑(Node 20+):

```bash
node cheatsheets/performance/bench-transaction.mjs   # 事务粒度:单事务 vs 逐条
node cheatsheets/performance/bench-compaction.mjs    # 日志四档体积、加载时间与墓碑
node cheatsheets/performance/bench-structure.mjs     # 编辑落点、嵌套深度、批量导入、大文本量级
```
