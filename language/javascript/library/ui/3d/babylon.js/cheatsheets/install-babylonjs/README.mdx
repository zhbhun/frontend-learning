# 安装

Babylon.js 以 ES module 形式发布，并按职责拆成一组带 `@babylonjs/` 作用域的包：渲染引擎、数学库、场景图在 `@babylonjs/core`；模型加载器、GUI、扩展材质、调试 Inspector、物理等各自单独成包，按需安装。npm 负责把包放进 `node_modules`，Vite 之类的构建工具负责解析 bare module 名并做 tree-shaking，HTTP 服务再把构建产物交给浏览器。它本身不绑定任何前端框架——一个空 Vite 项目加一个依赖就够。

最小本地项目只装 `@babylonjs/core`。本课用 `Engine.Version` 和一次引擎构造证明安装结果，不进入渲染循环；相机、网格和第一幅画面留给 [第一幅画面](?path=/docs/first-scene--docs)。

## 快速上手

从 Vite 的 `vanilla-ts` 模板起步（不需要 React/Vue），把 Babylon 当成纯模块依赖加入：

```sh
npm create vite@latest babylon-hello -- --template vanilla-ts
cd babylon-hello
npm install --save-exact @babylonjs/core@9.20.0
npm run dev
```

> 官方还提供 `create-babylonjs` 脚手架，预置了 ES6 + Vite 模板，已经把 tree-shakeable 导入和必要的副作用导入接好；想跳过手动接线时可以直接用它。本课为了看清每一层，仍从空 Vite 项目起步。

把 `index.html` 的 `<body>` 改成只有一个画布和模块入口：

```html
<canvas id="render"></canvas>
<script type="module" src="/main.ts"></script>
```

`main.ts` 只验证模块解析、版本和 WebGL 后端，不创建场景，也不开渲染循环：

```ts
import { Engine } from '@babylonjs/core';

const canvas = document.querySelector<HTMLCanvasElement>('#render')!;
// 只验证引擎可构造、WebGL 后端可用；不进入渲染（场景留给 1.2）
const engine = new Engine(canvas, true);

console.log('Babylon.js', Engine.Version);
console.log('WebGL 后端就绪');

engine.dispose();
```

打开 Vite 给出的本地地址。控制台应出现 Babylon.js 的版本横幅和 `Babylon.js 9.20.0`（或你实际安装的版本），紧跟着 `WebGL 后端就绪`。看到这两条就说明：包已安装、模块解析正常、WebGL 后端可用。

| 输入或状态 | 本课取值 | 改变后要注意什么 |
| --- | --- | --- |
| 项目依赖 | 只有 `@babylonjs/core@9.20.0` | 升级时核对 `Engine.Version` 与教程或 Playground 的版本是否一致 |
| 构建工具 | Vite（`vanilla-ts` 模板） | 改用 Webpack/Rollup 时保留 ESM 输出，否则 tree-shaking 失效 |
| 导入写法 | `import { Engine } from '@babylonjs/core'` | 改成 `import * as BABYLON` 会触发 barrel，bundle 体积明显变大 |
| 画布 | 一个空 `<canvas id="render">` | 引擎构造时画布必须已在 DOM 中，否则 `getContext` 返回 `null` |
| 运行方式 | Vite dev server（HTTP） | 不要 `file://` 直开；ES module 和 WebGL 都需要 HTTP 来源 |

## 分包与按需引入

`@babylonjs/*` 这组包共享同一条版本线和发布节奏，但按职责切分。`@babylonjs/core` 是唯一必装项，其余包用到再装，不提前引入。这种切分是它和「一个大包打天下」的遗留 `babylonjs` 包（见 [无构建运行](#无构建运行)）最大的区别：你只为用到的能力付 bundle 体积。

| 包 | 用途 | 何时安装 |
| --- | --- | --- |
| `@babylonjs/core` | 引擎、场景图、数学库、相机、光源、网格、内置材质与纹理 | 必装 |
| `@babylonjs/loaders` | glTF/GLB、OBJ、STL 等模型加载器 | 加载外部模型时 |
| `@babylonjs/gui` | 2D/3D UI 控件（按钮、面板、滑块） | 需要界面/HUD 时 |
| `@babylonjs/materials` | 扩展材质（水、火、梯度、三平面等） | 用到对应特效材质时 |
| `@babylonjs/inspector` | 运行时调试面板，叠加在场景上查场景树与性能 | 仅开发/调试时，按 devDependency 安装 |
| `@babylonjs/serializers` | 把 Scene/Mesh 序列化成 JSON | 需要导出场景时 |
| `@babylonjs/havok` | Havok 物理（WASM）插件 | 需要物理模拟时 |
| `@babylonjs/accessibility` | WebXR 与无障碍相关扩展 | 涉及 a11y 时 |

### 命名导入与 tree-shaking

从 `@babylonjs/core` 走命名导入，构建工具就能把没用到的类摇掉：

```ts
import { Engine, Scene, Vector3, MeshBuilder } from '@babylonjs/core';
```

三种写法的体积差别要分清：

```ts
// 推荐：只打包 Engine 等被引用的类
import { Engine } from '@babylonjs/core';

// 不推荐：命名空间导入会触发 barrel 文件，tree-shaking 难以生效
import * as BABYLON from '@babylonjs/core';

// 老式写法：来自遗留的 babylonjs 包，整包进 bundle，不可 tree-shaking
import * as BABYLON from 'babylonjs';
```

要让 tree-shaking 真正生效，构建工具必须保留 ESM 输出。Vite 默认就满足；Webpack 则别把 `@babylonjs/core` 转成 CommonJS——给 Babel 设 `modules: false`，或把包排除出会被转译的范围。

### 副作用导入（注册型模块）

Babylon 历史上在模块顶层做过注册型副作用，所以有些能力不靠命名导入拿类，而是靠「导入模块本身」把能力注册进引擎。这类导入不绑定到任何变量，只执行注册逻辑，放在第一次使用该能力之前：

```ts
// 注册 glTF 加载器，之后 SceneLoader 才认识 .gltf/.glb
import '@babylonjs/loaders/glTF';

// 注册 GUI 类型与默认主题
import '@babylonjs/gui';

// Inspector 也是副作用导入：导入即拿到全局调试入口
import '@babylonjs/inspector';
```

判断要不要副作用导入的简单办法：教程里用 `SceneLoader.ImportMesh` 加载 glTF 却加载失败，或 `AdvancedDynamicTexture.CreateFullscreenUI` 报找不到类型，多半是漏了对应的副作用导入（详见 [常见问题](#常见问题)）。

## 无构建运行

不想引入构建工具时，最直接的方式是用遗留的 `babylonjs` 包（不带作用域）的 UMD 构建，由官方 CDN 提供最新稳定版，全局挂载 `BABYLON`：

```html
<canvas id="render"></canvas>
<script src="https://cdn.babylonjs.com/babylon.js"></script>
<script>
  const engine = new BABYLON.Engine(document.getElementById('render'), true);
  console.log('Babylon.js', engine.Version);
  engine.dispose();
</script>
```

它只引用一个 `<script>`，适合最小演示和在线编辑器，但代价明确：整份引擎全量进页面，不能 tree-shaking，也不享受 `@babylonjs/*` 的模块化与按需引入。新项目不要从这里起步，只把它当作跑老示例或快速复现问题的参考。

如果你仍想在没有构建工具的情况下使用作用域包，可以用 import map 把 `@babylonjs/core` 这样的 bare specifier 映射到 CDN 上的 ESM 构建（jsdelivr、esm.sh 等都提供），项目里没有 `node_modules`：

```html
<script type="importmap">
  {
    "imports": {
      "@babylonjs/core": "https://cdn.jsdelivr.net/npm/@babylonjs/core@9.20.0/+esm"
    }
  }
</script>
```

> import map 里的 URL 与版本以 CDN 对应包页给出的 ESM 入口为准；用到 `@babylonjs/loaders/glTF`、`@babylonjs/gui` 等子路径时，要在 `imports` 里逐条补上映射，路径和大小写必须精确。

这种写法能跑，但没有构建工具就没有 tree-shaking，整份 core 仍会被拉进来；bare specifier 一多，import map 维护成本也快速上升。它适合一次性原型；需要离线开发、稳定依赖或生产构建时，回到 Vite 方案。

## 最佳实践

- 一个项目只用一套来源：要么全部 `@babylonjs/*` 同版本，要么遗留 `babylonjs`；混用会同时加载两份引擎，产生版本错位。
- 学习范例固定版本，并在控制台打印 `Engine.Version`；排查教程/Playground 行为差异时先比版本。
- 关心 bundle 体积就用命名导入；`import * as BABYLON from '@babylonjs/core'` 只在快速实验时使用。
- 副作用导入（loaders、gui、inspector 等）放在首次使用该能力之前；Inspector 只在开发环境引入，按 devDependency 安装。
- ESM 输出是 tree-shaking 的前提：Vite 默认满足，Webpack 别把 `@babylonjs/core` 转成 CommonJS。
- 始终通过 HTTP 打开示例，不要把 `file://` 下偶然能跑的结果当成正常环境。

## 常见问题

- 为什么 `SceneLoader.ImportMesh` 加载 glTF 报「不支持的扩展名」或直接失败？
  多半漏了副作用导入 `import '@babylonjs/loaders/glTF'`；OBJ/STL 等同理要导入对应模块。
- 为什么 bundle 体积没降，tree-shaking 像没生效？
  先确认是命名导入而非 `import * as BABYLON`；再检查构建工具是否保留了 ESM（Vite 默认满足，Webpack 别转 CommonJS）；注意部分注册型副作用模块本身不可摇掉，这是 Babylon 的已知特性。
- 为什么同时装了 `babylonjs` 和 `@babylonjs/core` 之后出现两套类型或行为不一致？
  这是混用了遗留包和作用域包，会加载两份引擎。统一成 `@babylonjs/*` 一套来源即可。
- 为什么浏览器直接报 `Failed to resolve module specifier "@babylonjs/core"`？
  bare specifier 不能被浏览器直接解析，需要 Vite/Webpack 这类构建工具，或一份映射到 CDN 的 import map。
- 为什么 `Engine.Version` 不是预期版本？
  检查 `package.json` 和 lock 文件里的实际版本，确认子包都来自同一版本，并排除浏览器或 CDN 缓存。
- 为什么 `new Engine(canvas)` 抛错或拿到 `null` context？
  通常不是安装问题，而是画布不在 DOM、画布被另一个上下文占用，或浏览器/GPU 不支持 WebGL；先在浏览器里确认 WebGL 可用。

## 总结回顾

摘要：

Babylon.js 用一组带 `@babylonjs/` 作用域的 ES module 包按职责拆分能力：`@babylonjs/core` 是必装核心，loaders、gui、materials、inspector、havok 等按需安装。最小项目用 Vite 加 `@babylonjs/core`，走命名导入让 tree-shaking 生效，注册型能力靠副作用导入，最后用 `Engine.Version` 和一次引擎构造核对版本与 WebGL 后端。无构建方案能用 UMD `<script>` 或 import map + CDN 跑通，但都失去 tree-shaking，只适合演示。

一句话：

> 安装闭环是「最小依赖 + 命名导入 + 副作用注册 + 版本与后端可观察」——`@babylonjs/core` 一个包、`Engine.Version` 一行日志就能验证。

知识要点：

- npm、Vite 和 HTTP 服务在最小 Babylon 项目里分别负责什么？
- 为什么 `@babylonjs/loaders`、`@babylonjs/gui` 等是按需安装，而 `@babylonjs/core` 是必装？
- 命名导入、命名空间导入和遗留 `babylonjs` 包在 bundle 体积上有什么差别？
- 什么时候需要副作用导入，遗漏会怎样表现？
- 怎样从「模块解析失败」「tree-shaking 失效」「glTF 加载失败」「版本不对」判断问题发生在哪一层？
