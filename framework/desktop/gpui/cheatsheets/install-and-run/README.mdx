# 安装与运行

GPUI 的安装分两层。Cargo 依赖一层：框架本体在 `gpui` crate，窗口与文本后端的选择由 `gpui_platform` crate 负责——它按宿主操作系统装配平台实现（macOS 用 Metal，Linux 选 Wayland/X11，Windows 用 Win32），平台差异通过 feature 表达。系统环境一层：macOS 需要 Xcode 命令行工具提供 Metal SDK，Linux 需要 Wayland/X11 开发库。

动手前先认清一个版本现实：GPUI 处于 pre-1.0，crates.io 的发布落后于仓库 main 分支。截至本课核对日（2026-10-06），crates.io 最新发布是 `gpui` 0.2.2（2025-10-22 发布），而官方 README 主推的 `gpui_platform` 尚未发布到 crates.io——照抄 README 的 `version = "*"` 会直接报找不到包。因此本课给出两条都能跑通的安装路径，并讲清它们如何互换。

本课建立最小闭环：创建 cargo 工程 → 配好依赖与系统环境 → 写约 50 行的最小窗口程序 → `cargo run` 验证。

| 回查项 | 当前状态（2026-10-06 核对） |
| --- | --- |
| `gpui`（crates.io） | 最新发布 `0.2.2`，2025-10-22 |
| `gpui_platform` | 仅存在于 main 分支，尚未发布到 crates.io |
| 应用入口 | git 口径用 `gpui_platform::application().run(..)`；0.2.x 发布版用 `gpui::Application::new().run(..)` |
| macOS feature | `font-kit`，缺少时排版正常但渲染不出字形 |
| Linux feature | `wayland`、`x11`，至少启用一个 |
| Windows feature | 无需任何 feature |
| Rust 工具链 | 最新 stable；已发布包使用 edition 2024（Rust 1.85+） |
| 运行命令 | `cargo run` |

## 安装 gpui

两条路径产生完全相同的工程结构，差别只在依赖来源和一行入口代码：crates.io 已发布版本开箱即用，git 跟随版本与官方 README 口径一致。先选定一条，再写 `Cargo.toml`。

### 已发布版本（crates.io）

```toml
gpui = "0.2"
```

0.2.2 是单 crate：全平台后端内置，默认 feature 已经是 `font-kit` 加 `wayland` 加 `x11` 加 `windows-manifest`，macOS 上零配置就有真实字形。适合今天就想跑起来的读者。版本约束写 `"0.2"` 只匹配 0.2.x，比 README 里的 `"*"` 更稳——pre-1.0 阶段次要版本之间就可能有破坏性变更。

### gpui 与 gpui_platform

官方 README（main 分支）当前的教学口径是两个 crate 分工：`gpui` 只含框架本体（`Entity`、`Element`、窗口 API），`gpui_platform` 依赖 `gpui`，并按编译目标引入对应平台实现（macOS 的 `gpui_macos`、Linux 的 `gpui_linux`、Windows 的 `gpui_windows`，以及 `gpui_wgpu`、`gpui_web`），你在 `gpui_platform` 上声明的 feature 会被转发到这些实现 crate。入口函数 `gpui_platform::application()` 替你挑选宿主平台的后端。官方 README 的跨平台默认配置：

```toml
gpui = { version = "*" }
gpui_platform = { version = "*", features = ["font-kit", "wayland", "x11"] }
```

但 `gpui_platform` 截至 2026-10-06 未发布到 crates.io，`version = "*"` 无法解析。可用的等价写法是 git 依赖，建议用 `rev` 锁定提交，避免 main 分支的日常变更破坏工程：

```toml
gpui = { git = "https://github.com/zed-industries/zed", rev = "85b3aa8" }
gpui_platform = { git = "https://github.com/zed-industries/zed", rev = "85b3aa8", features = ["font-kit", "wayland", "x11"] }
```

`85b3aa8` 是 2026-10-06 核对时的 main 分支 HEAD，两个依赖必须指向同一提交。等 `gpui_platform` 正式发布后，把 git 来源换回 `version` 即可，代码不用改。

### 平台 feature

| 平台 | feature | 作用 |
| --- | --- | --- |
| macOS | `font-kit` | 渲染始终走 Metal、无需 feature；但字形光栅化依赖 `font-kit`，缺少时 GPUI 回退到占位文本系统——文本布局正常，就是画不出字形 |
| Linux / FreeBSD | `wayland`、`x11` | 至少启用一个窗口后端；这两个 feature 会同时编译渲染器与文本系统，不需要单独的文本 feature |
| Windows | 无 | 窗口用 Win32、文本用 DirectWrite；`font-kit` 在此平台无效果 |

已发布的 0.2.2 默认开启上述全部 feature，无需手工配置；这组 feature 主要在两种场景下需要你显式声明：使用 `gpui_platform` 时（它默认无 feature），或对 `gpui` 设置了 `default-features = false` 做裁剪时。单平台开发可以只留本平台需要的项，例如 macOS 上仅保留 `font-kit`。

## 系统环境

Cargo 依赖装好只是第一步；平台后端在编译和链接时还需要系统级的 SDK 与开发库。缺什么、装什么，按下平台对号入座。

### macOS

GPUI 用 Metal 渲染，Metal 的 SDK 和链接工具由 Xcode 提供。官方 README 要求三步：

```sh
# 1. 从 App Store 或 Apple Developer 网站安装 Xcode，并启动一次以装好 macOS 组件
# 2. 安装 Xcode 命令行工具
xcode-select --install
# 3. 让命令行工具指向新装的完整 Xcode
sudo xcode-select --switch /Applications/Xcode.app/Contents/Developer
```

第 2 步给编译器与链接器，第 3 步保证它们用的是完整 Xcode 里的 macOS SDK，而不是旧路径下的残留版本。

### Linux

README 未列出包名，官方给出的安装入口是仓库里的 `script/linux` 脚本，它按发行版自动安装依赖（面向编译整个 Zed，GPUI 只需其中一部分）。Ubuntu/Debian 上与 GPUI 直接相关的常见项：

```sh
sudo apt install libwayland-dev libxkbcommon-x11-dev libx11-xcb-dev libfontconfig-dev
```

缺少哪类库对应哪类 feature：`wayland` feature 依赖 `libwayland-dev` 一族，`x11` feature 依赖 X11/xkbcommon 相关开发包。只装其中一个后端的库时，feature 也相应只开一个。

### Windows

无需额外系统依赖：窗口走 Win32、文本走 DirectWrite，系统自带。`font-kit` 在此平台无效，加了也不报错但不起作用。

### Rust 工具链

官方 README 要求最新版 stable Rust。已发布的 0.2.2 使用 edition 2024，需要 Rust 1.85 及以上；工具链过旧会在编译时报 edition 2024 不支持。用 rustup 的读者执行 `rustup update` 即可对齐。

## 第一个窗口

### 建工程与依赖

```sh
cargo new hello-gpui
cd hello-gpui
```

把选定路径的依赖写进 `Cargo.toml`（见「安装 gpui」），本节代码按 git 口径书写；用 0.2.x 发布版的读者只需改入口两行，见本节末尾。

### 最小窗口程序

整个程序只做三件事：启动应用、开一个窗口、为窗口注册一个会渲染的根视图。替换 `src/main.rs`：

```rust
use gpui::{
    App, Bounds, Context, SharedString, Window, WindowBounds, WindowOptions, div, prelude::*, px,
    rgb, size,
};
use gpui_platform::application;

// 根视图：一个实现 Render 的普通结构体，GPUI 每帧调用它的 render 方法。
struct HelloWorld {
    text: SharedString,
}

impl Render for HelloWorld {
    fn render(&mut self, _window: &mut Window, _cx: &mut Context<Self>) -> impl IntoElement {
        div()
            .size(px(500.0)) // 内容区 500x500
            .bg(rgb(0x505050)) // 灰色背景
            .border_1()
            .border_color(rgb(0x0000ff)) // 1px 蓝色边框
            .justify_center() // 主轴居中
            .items_center() // 交叉轴居中
            .text_xl()
            .text_color(rgb(0xffffff)) // 白色文字
            .child(format!("Hello, {}!", self.text))
    }
}

fn main() {
    // application() 按宿主 OS 挑选窗口与文本后端；run() 启动平台事件循环，
    // 闭包拿到 &mut App，是整个应用的装配点。
    application().run(|cx: &mut App| {
        // 在屏幕居中处取一块 500x500 的区域作为窗口初始位置
        let bounds = Bounds::centered(None, size(px(500.0), px(500.0)), cx);
        cx.open_window(
            WindowOptions {
                window_bounds: Some(WindowBounds::Windowed(bounds)),
                ..Default::default()
            },
            |_, cx| {
                // cx.new 把结构体包成 GPUI 托管的 Entity，作为窗口根视图
                cx.new(|_| HelloWorld {
                    text: "World".into(),
                })
            },
        )
        .unwrap();
        // 把应用带到前台
        cx.activate(true);
    });
}
```

三个环节对应三段代码。入口处，`application().run()` 创建 `Application` 并传入回调，事件循环从这里接管。开窗处，`cx.open_window()` 接收 `WindowOptions`（初始位置、大小等窗口属性）和一个构造根视图的闭包，返回的 `WindowHandle` 用 `unwrap` 暴露开窗失败的情况。视图处，`HelloWorld` 实现 `Render` trait，`render` 方法返回一棵元素树——这里是一个 `div`，用 Tailwind 风格的链式方法声明样式，GPUI 负责布局并画成像素；`div` 的完整样式体系在后续布局课程展开。

使用 0.2.x 发布版的读者，把入口换成 `Application::new()`，其余闭包体一字不改：

```rust
use gpui::Application; // 替代 use gpui_platform::application;

fn main() {
    Application::new().run(|cx: &mut App| {
        // 闭包体与上面的版本完全一致
    });
}
```

## 运行验证

```sh
cargo run
```

首次编译要拉起整棵依赖树，耗时从几十秒到几分钟不等，属正常现象。构建完成后，逐项核对窗口表现，每一项都对应一个配置点：

- 屏幕中央出现 500x500 窗口——入口与 `open_window` 工作正常；
- 灰色背景带 1px 蓝色边框——`div` 样式生效；
- 居中显示白色 `Hello, World!`，字形清晰——`font-kit` 生效；若文字缺失但排版占位存在，回到「平台 feature」检查。

看到这三项，环境闭环完成，后续所有课程都跑在这个工程结构上。

## 常见问题

- 报错 `error: no matching package named gpui_platform found`，照抄的是官方 README 的 `version = "*"` 写法
  这是预期内的失败：`gpui_platform` 截至 2026-10-06 未发布到 crates.io。改用 git 依赖（见「gpui 与 gpui_platform」），或退回已发布的 `gpui = "0.2"` 并把入口换成 `Application::new()`。

- macOS 上窗口正常出现，但文字不渲染，只能看到空白的排版占位
  给依赖补上 `font-kit` feature。`gpui = "0.2"` 默认已开启；git 口径下 `gpui_platform` 默认没有任何 feature，`features` 列表里必须显式包含 `"font-kit"`。占位文本系统只做布局，不产出字形，所以现象是「文字位置对、笔画不存在」。

- macOS 编译在链接阶段报错，提示找不到 SDK 或系统头文件
  执行 `xcode-select --install` 安装命令行工具；装过完整 Xcode 的再执行 `sudo xcode-select --switch /Applications/Xcode.app/Contents/Developer` 对齐 SDK 路径。Metal 渲染依赖完整 Xcode 提供的 macOS SDK，只有 CLT 或路径指向旧版本时会出现这类链接失败。

- Linux 编译失败，提示找不到 wayland 或 xkbcommon 的头文件
  安装对应开发库：`sudo apt install libwayland-dev libxkbcommon-x11-dev libx11-xcb-dev libfontconfig-dev`（Ubuntu/Debian，其他发行版安装同名库）。判断依据：`wayland`、`x11` feature 编译时需要这些 C 库的头文件，包管理器里缺的就是带 `-dev`/`-devel` 后缀的开发包。

## 总结回顾

摘要：

GPUI 的安装由 Cargo 依赖和系统环境两层组成。Cargo 侧有两条可跑通的路径：crates.io 已发布的 `gpui = "0.2"`（0.2.2，单 crate 内置全平台后端，默认 feature 齐全），以及官方 README 口径的 `gpui` 加 `gpui_platform` 双 crate——后者尚未发布，需以 git 依赖引入并用 `rev` 锁定。平台差异收敛在 feature 上：macOS 的字形靠 `font-kit`，Linux 至少启用 `wayland` 或 `x11` 之一，Windows 无需配置。系统侧，macOS 要装 Xcode 与命令行工具对齐 Metal SDK，Linux 要补 Wayland/X11 开发库。最小窗口程序由三步构成：`application()` 或 `Application::new()` 启动事件循环，`cx.open_window()` 配置并创建窗口，实现 `Render` 的根视图声明界面；`cargo run` 后按「窗口出现、样式生效、字形清晰」三项验证。

一句话：

> 装 GPUI 先选路径——今天能跑用 `gpui = "0.2"`，跟官方口径用 git 引入 `gpui` 加 `gpui_platform`；macOS 想要真实字形，认准 `font-kit`。

知识要点：

- `gpui` 与 `gpui_platform` 各自负责什么，平台 feature 声明在哪个 crate 上
- 截至 2026-10-06，crates.io 上的最新版本号与发布日期，`gpui_platform` 的发布状态
- 两条安装路径的 `Cargo.toml` 写法，以及入口代码 `application()` 与 `Application::new()` 的对应关系
- macOS 缺少 `font-kit` 时会看到什么现象，如何补上
- Linux 上 `wayland` 与 `x11` feature 的取舍，缺开发库时的处理办法
- 最小窗口程序的三步结构，以及运行验证要核对的三个观察点
